# خطة تنفيذ الدفع عند الاستلام للمزادات

## الهدف والنطاق

تجعل هذه الخطة **الدفع عند الاستلام** وسيلة تحصيل حقيقية للطلب الناتج عن مزاد فائز. لا يبدأ تجهيز أو شحن القطعة قبل أن يؤكد الفائز التزامه بالطلب ويختار التوصيل أو الاستلام الذاتي. لا يصبح صافي البائع متاحاً للسحب إلا بعد إثبات التحصيل والتسليم، مع احتفاظ المنصة بعمولتها المسجلة على الطلب.

تبدأ الدفعة الأولى في السوق السعودي وبإدارة تشغيل يدوية داخل لوحة الإدارة. لا تتضمن هذه الدفعة ربط شركة شحن خارجية تلقائياً؛ يمكن لفريق التشغيل إنشاء الشحنة وإضافة رقم التتبع أو رمز الاستلام، ثم يصبح ربط شركة الشحن مرحلة لاحقة من دون تغيير منطق الطلب.

## قواعد العمل المقترحة لاعتماد المالك

| القرار | القاعدة المقترحة | سببها |
|---|---|---|
| إتاحة الدفع عند الاستلام | للحسابات النشطة والموثقة فقط، وفق سياسة السوق | تقليل المزايدات غير الجادة وطلبات الرفض |
| مهلة تأكيد الفائز | قيمة قابلة للضبط لكل سوق، تعرض بوضوح في الطلب | لا يبقى المنتج محجوزاً بلا نهاية |
| وسائل التسليم | توصيل أو استلام ذاتي، يحدد البائع المتاح منها قبل المزاد | لا يختار الفائز وسيلة غير ممكنة للقطعة |
| مبلغ التحصيل | سعر الفوز + رسوم شحن معروضة صراحة، إن وجدت | لا توجد رسوم مفاجئة عند التسليم |
| استلام المال | يجمعه المندوب أو نقطة الاستلام لصالح المنصة، وليس البائع مباشرة | تمكين احتساب العمولة والتسوية المنضبطة |
| رفض أو تعذر التحصيل | إلغاء الطلب مع سجل محاولة، وإيقاف مؤقت أو مراجعة للحساب وفق السياسة | حماية البائع والمخزون من تكرار عدم الجدية |
| إتاحة مستحق البائع | بعد التحصيل والتسليم وتأكيد الاستلام أو انقضاء مهلة اعتراض قابلة للضبط | لا يتم السحب قبل اكتمال الالتزام |

## حالات الطلب والتحصيل

> لا يكفي استخدام حقل حالة واحد للطلب، لأن الدفع والتوصيل والتسوية ثلاث حالات مستقلة. ستبقى حالة الطلب للعرض العام، مع حفظ حالات مالية وتشغيلية منفصلة تمنع تراجع الحالة عند تحديث الشحنة أو التحصيل.

| المجال | الحالات الجديدة أو المعدلة | الانتقال المسؤول |
|---|---|---|
| الطلب | `awaiting_cod_confirmation` → `cod_confirmed` → `fulfillment_pending` → `shipped` أو `ready_for_pickup` → `completed` | الفائز ثم فريق التشغيل ثم إثبات التسليم |
| التحصيل | `awaiting_collection` → `collected` أو `collection_failed` أو `cancelled` | فريق التشغيل أو تكامل شركة الشحن لاحقاً |
| التسوية | `not_due` → `pending_release` → `released` أو `held` | النظام بعد التحصيل والتسليم، أو فريق المالية عند وجود اعتراض |
| الشحنة | `pending` → `prepared` → `shipped` أو `ready_for_pickup` → `delivered` | مستخدم يملك صلاحية التشغيل في السوق نفسه |

عند إغلاق المزاد بفائز، ينشئ النظام طلباً بحالة `awaiting_cod_confirmation` ودفعة تحصيل واحدة بحالة `awaiting_collection` وطريقة `cash_on_delivery`. يحتفظ الطلب بسعر الفوز، نسبة العمولة، مبلغها، وصافي البائع كلقطة تاريخية كما هو الحال الآن.

بعد تأكيد العميل، يلتقط النظام عنوان التوصيل أو اختيار الاستلام الذاتي كنسخة مرتبطة بالطلب، ويسجل وقت التأكيد ووقت انتهاء المهلة. بعد ذلك فقط يستطيع فريق التشغيل تجهيز الشحنة. عند استلام المبلغ فعلياً، يسجل المستخدم المخوّل المبلغ المحصل ومرجع التحصيل، وتتحول الدفعة إلى `collected` من دون افتراض نجاح تلقائي.

## التغييرات التقنية المطلوبة

| الطبقة | التغيير | ضابط الأمان |
|---|---|---|
| قاعدة البيانات | إضافة طريقة الدفع، مهلة تأكيد الفائز، وقت التأكيد، طريقة التسليم، رسوم الشحن، إجمالي التحصيل، وحالة التسوية إلى الطلب؛ إضافة وقت/مرجع/نتيجة التحصيل إلى الدفعة | ترحيل غير هدمي، قيم افتراضية آمنة، وحفظ اللقطات التاريخية |
| منطق المزاد | إنشاء طلب COD عند اختيار السوق للدفع عند الاستلام وإشعار الفائز والبائع | إنشاء واحد فقط لكل مزاد وقفل قاعدة البيانات الحالي |
| واجهات API | تأكيد طلب COD، حفظ عنوان أو استلام ذاتي، تسجيل تحصيل، تسجيل فشل التحصيل، تأكيد استلام المشتري، وتحرير مستحق البائع | ملكية المشتري، صلاحيات تشغيل/مالية، ونطاق السوق في كل مسار |
| الشحن | السماح بإنشاء الشحنة بعد `cod_confirmed` بدلاً من اشتراط الدفع الإلكتروني فقط | لا يسمح بالشحن قبل تأكيد الفائز ولا بتجاوز انتقالات الحالة |
| المحفظة | إبقاء صافي البائع معلقاً ثم نقل المبلغ إلى المتاح بسجل حركات غير قابل للتكرار | منع التكرار بالمفاتيح المرجعية والقفل داخل المعاملة |
| سجل النشاط | تسجيل تأكيد الفائز، اختيار التسليم، التحصيل أو الفشل، التوصيل، تحرير الرصيد، والإيقاف التشغيلي | تتبع قابل للمراجعة دون كشف بيانات أكثر من اللازم |

## الواجهات المطلوبة

| المستخدم | الشاشة أو الإجراء | النتيجة الظاهرة |
|---|---|---|
| الفائز | صفحة «لقد ربحت المزاد» وطلب جديد في الحساب | السعر النهائي، العمولة، رسوم الشحن، عداد مهلة التأكيد، وزر «تأكيد الطلب» |
| الفائز | اختيار توصيل أو استلام ذاتي | عنوان محفوظ للطلب أو تعليمات/رمز استلام، وليس تحريراً بعد الشحن |
| الفائز | تتبع الطلب وتأكيد الاستلام | خط زمني واضح وإبلاغ عن الشحن أو الجاهزية أو اكتمال الطلب |
| البائع | بطاقة طلب مبيع | تأكيد أن القطعة قيد التجهيز، ومنع عرض المال كمتاح قبل التسوية |
| فريق التشغيل | قائمة «طلبات عند الاستلام» | فلترة حسب انتهاء المهلة، التجهيز، الشحن، التحصيل، الفشل، والاستلام الذاتي |
| فريق المالية | قائمة التسويات المعلقة | اعتماد أو حجز أو تحرير صافي البائع بعد اكتمال شروطه |

### خريطة الواجهات المقترحة

| الواجهة | المسار المقترح | المسؤول | البيانات أو الأفعال الرئيسية |
|---|---|---|---|
| نتيجة فوز المزاد | `/orders/{reference}` | الفائز | تأكيد الطلب، العنوان أو الاستلام الذاتي، المهلة، الإجمالي، وخط زمني للحالة |
| طلباتي | `/account#orders` ثم تفاصيل الطلب | الفائز والبائع | بطاقات حالة قابلة للفتح، لا تعرض إجراءً لا يملك صاحبه صلاحيته |
| طلبات البائع | `/account#sales` | البائع | تجهيز القطعة، تعليمات التسليم، وصافي مستحق معلق فقط |
| قائمة تشغيل COD | لوحة الإدارة: الطلبات عند الاستلام | فريق التشغيل | إنشاء الشحنة، رقم التتبع، رمز الاستلام، تسجيل التحصيل أو الفشل |
| التسويات | لوحة الإدارة: المالية | فريق المالية | مراجعة التحصيل والتسليم ثم تحرير صافي البائع أو حجزه |

## مراحل التنفيذ

### المرحلة الأولى: أساسات الطلب والتحصيل

تتضمن ترحيلات البيانات، حالات الطلب والتحصيل والتسوية، منطق انتهاء مهلة التأكيد، وسجل النشاط. يضاف مسار تأكيد الفائز وتسجيل التحصيل اليدوي، مع اختبارات عزل السوق وتكرار الطلب وتكرار تسجيل التحصيل.

### المرحلة الثانية: تجربة العميل والبائع

تتضمن صفحة فوز للمشتري، تفاصيل الطلب، اختيار التوصيل أو الاستلام الذاتي، عرض المهلة، تتبع الحالة، واجهة البائع، وإشعارات واضحة. لا تعرض الواجهة أي وعد دفع أو تتبع ما لم تصل بيانات حية من الخدمة.

### المرحلة الثالثة: التشغيل والتسوية

تتضمن قوائم التشغيل في لوحة الإدارة، تسجيل الفشل أو الإلغاء، رقم التتبع أو رمز الاستلام، تأكيد الاستلام، ونقل صافي البائع من المعلق إلى المتاح. تبقى كل عملية مالية قابلة للتدقيق وغير قابلة للتكرار.

### المهلات والمهام الدورية

لا تعتمد الخطة على مؤقت داخل خدمة Render أو على `setInterval` أو `node-cron`؛ إذ لا يكون ذلك موثوقاً عندما تتوقف الخدمة المجانية عند الخمول. في الدفعة الأولى، تظهر الطلبات المنتهية في قائمة تشغيل واضحة، ويجري إغلاقها يدوياً من مستخدم مخوّل مع سبب مسجل. بعد إثبات المسار الأساسي، تضاف مهمة HTTP دورية مستقلة ومحمية لتنفيذ: إغلاق تأكيدات الفائز المتأخرة، إرسال تذكير قبل انتهاء المهلة، ووضع التسويات التي تجاوزت مهلة الاعتراض في قائمة التحرير.

تكون هذه المهمة قابلة لإعادة التنفيذ بأمان: تبحث عن الطلبات المؤهلة بحالتها ووقتها الفعليين، وتقفل السجل قبل التعديل، ولا تعتمد على اسم المهمة أو بيانات طلب خارجية لتحديد الطلب. لا تُنشأ أو تُشغّل أية مهمة دورية قبل نشر نقطة النهاية واختبارها في الإنتاج.

### المرحلة الرابعة: الإطلاق المراقب

يبدأ المسار في السوق السعودي وعلى طلبات ضمن سياسة الأهلية المعتمدة. تشمل قائمة التحقق: اختبار طلب ناجح، تأكيد متأخر، رفض فائز، فشل تحصيل، توصيل، استلام ذاتي، تحرير رصيد، وحماية الصلاحيات ونطاق السوق. لا يُعمم على أسواق أخرى قبل تحقق التشغيل الواقعي.

## معايير القبول قبل النشر

1. لا يستطيع شخص غير الفائز تأكيد طلب COD أو تغيير عنوانه.
2. لا يستطيع فريق خارج سوق الطلب تسجيل الشحن أو التحصيل أو التسوية.
3. لا تنشأ أكثر من دفعة تحصيل أو تسوية للمزاد نفسه.
4. لا تنتقل القطعة إلى الشحن قبل تأكيد الفائز.
5. لا يصبح صافي البائع متاحاً للسحب قبل إثبات التحصيل والتسليم.
6. يظهر للمشتري السعر الإجمالي وحالة الطلب ووسيلة الاستلام ببيانات حية فقط.
7. تبقى الطلبات القديمة ومسار الدفع الإلكتروني الحالي دون تعديل أو إعادة احتساب.

## قرارات مطلوبة قبل بدء التنفيذ

يحتاج التنفيذ موافقة المالك على: مهلة تأكيد الفائز، هل الاستلام الذاتي متاح من الدفعة الأولى، من يستلم النقد عملياً، سياسة الإلغاء أو عدم الاستلام، الحد الأقصى لقيمة طلب COD، ومدة انتظار اعتراض المشتري قبل تحرير صافي البائع. إذا لم تُحدد هذه القيم، ستبقى متغيرات إعداد لكل سوق ولا تُفترض قيم مالية أو تشغيلية من تلقاء نفسها.
